# Script Review Checklist

## Purpose

Every GFriend script generated by the AI Agent is a **draft that requires developer review before use**. This checklist ensures scripts are syntactically correct, semantically sound, and safe to execute.

A script is **review-complete** when a developer has checked every item in this list.

---

## Quick Classification

Before detailed review, classify the script's status from the `generation_report.json` or the script header:

| Header Status | Meaning | Action |
|--------------|---------|--------|
| `PASSED` | No validation warnings | Still do full review — validator checks syntax, not logic |
| `WARNING(N)` | N items flagged for attention | Pay extra attention to `// WARNING` lines |
| `ERROR(N)` | Syntax or structural issues | Fix errors first, then do full review |
| `GENERATION_FAILED` | Script could not be generated | Write manually or re-run with more context |

---

## Section 1 — Script Header Review

| # | Check | How to Verify |
|---|-------|--------------|
| 1.1 | TC ID in header matches the expected test case | Compare `// TC ID:` line to TestRail/template |
| 1.2 | TC Title accurately describes the test | Read `// TC Title:` line |
| 1.3 | Script is marked as DRAFT | `// Status: DRAFT` line is present |

---

## Section 2 — Variable Declarations

| # | Check | How to Verify | Common Mistakes |
|---|-------|--------------|-----------------|
| 2.1 | All device addresses use variables, not hardcoded IPs | Look for raw IP addresses (e.g., `192.168.1.`) in keyword calls | IP hardcoded in keyword params instead of `${DUT_Address}` |
| 2.2 | All credentials use variables | No plaintext passwords in keyword calls | `Web.Set Text(#pass, Admin@123)` instead of `${Password}` |
| 2.3 | System variables used where appropriate | `${DUT_AdminID}`, `${DUT_AdminPW}` for device credentials | Agent declaring new variables that should use system ones |
| 2.4 | Variable names follow `${VarName}` syntax | Regex: `\$\{[A-Za-z0-9_-]+\}` | Missing `$` or `{}` |
| 2.5 | Variable values are appropriate defaults | No production passwords as defaults | Use `testuser`, `Test@123` style placeholders |
| 2.6 | `.gfvar` file referenced where team-shared variables exist | Check if project has a shared variable file | Agent declaring variables that are already in a .gfvar |

---

## Section 3 — Using Statements

| # | Check | How to Verify | Common Mistakes |
|---|-------|--------------|-----------------|
| 3.1 | A `using` statement exists for every library referenced in the test body | List all `LibraryName.Keyword` calls, ensure each library is in a `using` line | Agent references `JediOmni.Touch Text` but no `using JediOmni` |
| 3.2 | Device IDs match your test environment (`With` clause) | Compare `With DeviceID` to GFriendUI device list | Wrong device ID or missing `With` for multi-device TC |
| 3.3 | Aliases (`As` clause) used consistently | Every keyword call using an alias must match the `As` name exactly | `using Android As Phone`, but calls use `Android.Touch Text` |
| 3.4 | Remote execution (`At` clause) present for remote TCs | If TC runs on a remote agent, `At RemoteAgentID` must be in using statement | Missing `At` for remote device |
| 3.5 | No duplicate using statements | Each library declared once (unless multiple instances with different aliases) | `using Web` appears twice |

---

## Section 4 — Test Case Block

| # | Check | How to Verify | Common Mistakes |
|---|-------|--------------|-----------------|
| 4.1 | Test case name matches TC title (or is a reasonable abbreviation) | Compare test case block name to TC_Title field | Generic name like "Test Case 1" instead of meaningful name |
| 4.2 | Test case block `{` and `}` are balanced | Count braces — 1 open, 1 close per level | Unclosed brace (validator catches this) |
| 4.3 | All manual test steps are represented by at least one keyword | Map each step to corresponding line(s) in script | Steps 4–6 skipped, no keyword generated |
| 4.4 | **Unmapped steps marked with `// UNIMPLEMENTED` or `// WARNING`** | Check for these markers — review if step is truly unautomatable or if a keyword exists | Agent marks step as unimplemented when a keyword actually exists |
| 4.5 | Steps are in correct order | Follow the step numbering from the TC | Steps reversed or out of order |
| 4.6 | Preconditions handled (as setup keywords or variable defaults) | Preconditions referencing addresses/credentials are reflected in variables | Precondition "printer at 192.168.1.50" not reflected in script |

**Note on Unmapped Steps:** See [Agent Workflow Spec — Step 9.5: Guardrails](05_Agent_Workflow_Spec.md#step-95--guardrails-handling-unmapped-test-steps) for details on how the agent handles test steps with no matching keywords.

---

## Section 5 — Keyword Correctness

| # | Check | How to Verify | Common Mistakes |
|---|-------|--------------|-----------------|
| 5.1 | All generated keywords exist in the GFriend keyword library | Check each `Library.Keyword(...)` against the keyword docs or IDE autocomplete | Agent invents `Web.Login(user, pass)` which doesn't exist |
| 5.2 | Keywords have correct parameter count | Compare to keyword definition signature | `Web.Set Text(selector)` — missing second `text` parameter |
| 5.3 | Selectors/IDs are placeholders, not real values | CSS selectors like `#username`, IDs like `loginButton` need verification with actual app | Agent uses wrong element ID guessed from TC text |
| 5.4 | Wait timeouts are realistic for the tested system | `JediOmni.Wait For Text(Ready, 10)` — is 10 seconds enough for a printer? | Too short timeout (10s) for slow printers — should be 60–120s |
| 5.5 | `Sleep()` values are in seconds and reasonable | `Sleep(5)` = 5 second wait | `Sleep(5000)` (milliseconds — wrong), or `Sleep(0.5)` (too short) |
| 5.6 | `// WARNING` annotations reviewed and resolved | Grep for `// WARNING` in generated script | Leaving WARNING comments without fixing them |

---

## Section 6 — Flow Control

| # | Check | How to Verify | Common Mistakes |
|---|-------|--------------|-----------------|
| 6.1 | `If/Fail/Error` blocks used appropriately for conditional steps | If TC says "if X appears, do Y" — check If block generated | Missing conditional handling for optional UI elements |
| 6.2 | `While` loops have a sensible maximum iteration count | `While:Condition:50` — is 50 iterations appropriate? | Default 50 may be too many or too few for specific scenarios |
| 6.3 | `Repeat` blocks used only for genuinely repetitive steps | Repeat used for load/stress within a single TC | Single-run TC incorrectly wrapped in Repeat |
| 6.4 | No unnecessary `Repeat:1` blocks | `Repeat:1` is pointless | Agent adds Repeat when none was needed |

---

## Section 7 — Evidence Collection

| # | Check | How to Verify | Common Mistakes |
|---|-------|--------------|-----------------|
| 7.1 | `Capture Screen Shot` before key verification steps | Each assertion step (Wait For Text, Check Text Exists) should be preceded by a screenshot | Screenshot only at end, missing evidence for intermediate steps |
| 7.2 | Screenshot names are meaningful | `Web.Capture Screen Shot(Dashboard_After_Login)` not `screenshot1` | Generic screenshot names |
| 7.3 | Sufficient screenshots per the evidence plan requirements | Minimum: 1 per test case. Recommended: 1 per major step | No screenshots at all |

---

## Section 8 — Safety Checks

| # | Check | How to Verify | Common Mistakes |
|---|-------|--------------|-----------------|
| 8.1 | `AlwaysPass` is NOT present anywhere in the script | `grep AlwaysPass TC-001.txt` should return nothing | Agent accidentally adding AlwaysPass (validator should catch this) |
| 8.2 | Script does not hardcode production credentials | No `admin` / `password123` / real customer credentials | Agent copied credentials from TC notes |
| 8.3 | Script will not cause destructive actions on the DUT | No keywords that delete data, reset firmware, or irreversibly change state — unless TC specifically requires it | Accidental factory reset keyword |
| 8.4 | `Pass()` / `Fail()` not used to override genuine results | These should only appear when TC explicitly requires forced result | Agent adds `Pass()` at end thinking it's a closing statement |

---

## Section 9 — Final Approval

| # | Check |
|---|-------|
| 9.1 | Remove or resolve all `// WARNING` and `// TODO` comments before finalizing |
| 9.2 | Replace all placeholder selectors with actual tested element IDs |
| 9.3 | Run the script in GFriendUI (dry run / single pass) to confirm no execution errors |
| 9.4 | Confirm script passes at least once against the real DUT |
| 9.5 | Remove `// Status: DRAFT` header line (or change to `REVIEWED`) |
| 9.6 | Commit to GitHub per the SCL Automation Evidence Plan workflow |

---

## Review Outcome Classification

After completing the checklist, classify the script as:

| Classification | Criteria | Action |
|---------------|----------|--------|
| **Approved — Minor Edits** | Only selector/parameter changes needed (≤ 30% of keywords) | Edit and commit |
| **Approved — Logic Intact** | No edits needed, script is complete and correct | Commit as-is |
| **Needs Rework** | Missing steps, wrong library, structural issues (> 30% of keywords wrong) | Significant edit required |
| **Rejected — Rewrite** | Script does not reflect TC, wrong domain, fundamentally incorrect | Discard and write manually; report issue to AI Agent team |

Track this classification in `generation_report.json` for continuous improvement metrics.
